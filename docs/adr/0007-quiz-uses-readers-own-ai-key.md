# ADR-0007: Quizzes call an AI provider directly with the reader's own API key

Status: accepted

## Context

The app is getting a Quiz feature: an AI writes true/false and multiple-choice questions about the pages a reader has already read. Two routes were considered: the reader supplies their own AI API key (for example a Google AI Studio key) and the app calls the provider, or the Book is fed to Google's NotebookLM to produce questions.

NotebookLM has no public API for individual users (only an enterprise offering on Google Cloud), so using it would mean the reader uploads the Book, generates questions and copies them back by hand. The app could not tie questions to the Last-read position, score attempts or cache them. This app is client-only with no backend, and running one to hold a shared AI key and pay for every reader's usage was rejected as disproportionate for a non-commercial project (the same reasoning as ADR-0004).

## Decision

1. Quizzes are generated by calling an AI provider directly from the app with the reader's own API key. Google Gemini is the default provider.
2. `/packages/core` defines a platform-agnostic provider interface (strategy pattern) and a factory that picks the implementation, so another provider can be added without changing what a Quiz is. Only the Gemini implementation ships first.
3. The API key is entered in Settings, stored encrypted by the operating system (Electron `safeStorage` on desktop), kept on this device, and never synced or logged.
4. Only the text of the Quiz scope, which never extends past the Last-read position, is sent to the provider. The reader gets a one-time notice on their first Quiz, plus a line in Settings, that this text goes to the provider.
5. Generated Quiz questions and Quiz attempts are stored per Book by content hash, device-local, so a Retake with the same questions costs nothing and works offline.

## Consequences

- Cost, quota and rate limits belong to the reader's own key and account. A missing key, a bad key, a rate limit or being offline shows a clear message and never blocks reading.
- Nothing is proxied through a server we run, so there is no shared secret to protect and no bill for us, but the feature is unusable until the reader gets a key.
- Scanned PDFs with no extractable text are not supported; the reader sees a clear message instead.
- Book text leaves the device for a third party, which is why the privacy notice is required.
- Moving to a hosted, keyless service later would need a backend this project does not have, and would change the privacy story.

## Alternatives considered

- **NotebookLM.** Rejected: no public consumer API, so the flow is manual and cannot be scored, cached or tied to reading progress.
- **A backend holding a shared AI key.** Rejected: adds a server, an ongoing bill and abuse handling to a client-only, non-commercial app.
- **Local or on-device model.** Rejected for v1: works offline but needs a heavy model download and gives lower question quality; the provider interface leaves room to add it later.
